# Rules inside the managed .gitignore block are erased by devteam sync

**Origin:** Supabase local stack artifacts showing as untracked | 2026-10-10
**Tags:** gitignore, managed block, devteam sync, dev-team-agents (managed), infra/supabase/.local, untracked, regenerated

> `devteam sync` regenerates everything between `# >>> dev-team-agents (managed)` and `# <<< dev-team-agents (managed)`. A project rule added inside that block is silently dropped on the next sync. Put project rules after the block.

---

## What it is

`.gitignore` in this repository holds a block owned by `devteam sync`, marked "regenerated by `devteam sync`,
do not edit". Rules outside the markers belong to the project and survive a sync.

## How it works

1. A rule for `infra/supabase/.local/` was added inside the managed block (commit 48fbd2d).
2. A later `devteam sync` rewrote the block from its template and dropped the rule.
3. `infra/supabase/.local/` (local Ed25519 signing key, ban pepper, database copy) then showed as untracked.
4. The fix (commit 3557ea5) placed the rules after the closing marker:

```gitignore
# Supabase: local stack from infra/supabase/dev-local.sh (secrets, database copy) and
# the project link written by `supabase link`. Outside the managed block, which sync rewrites.
infra/supabase/.local/
infra/supabase/.temp/
infra/.temp/
```

## Gotchas

- The failure that matters is secret exposure: `infra/supabase/.local/` holds the signing key, so an untracked
  `.local/` is the warning sign to act on, not a cosmetic status line.
