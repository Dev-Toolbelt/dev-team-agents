# ADR-0012: Project layout version and a consented structure upgrade

**Date:** 2026-09-27
**Status:** Accepted
**Deciders:** dev-team-agents maintainers

## Context

ADR-0007 and ADR-0008 move a project's memory — `session-summary.md`, `state.json`, the audit log —
out of the project and into `data/projects/<project_id>/`, so the project keeps only its identity
and regenerable artifacts. Milestone M1 shipped the identity and left the memory where it was.

Relocating it touches data that exists nowhere else, in projects the user has been working in for
months. Three strategies were on the table, and the one that looks cheapest is the one that fails
worst:

- **Move it during `sync`.** `sync --all` runs after every update, so the relocation would happen
  as a side effect of an unrelated command, on ten projects at once, with no moment at which the
  user chose it.
- **Dual-write for a deprecation cycle.** Nothing breaks and nothing is lost, but the same fact
  then lives in two places with no owner — precisely the state-ownership defect the M1 review
  raised about `installed_version`, adopted deliberately this time.
- **Hard cutover.** Clean, and it silently strands the memory of every project that has not run the
  new code yet.

## Decision

The project records **which layout it is on**, and nothing moves without the user asking.

`.dev-team-agents/project.json` gains a `layout` integer, distinct from `schema`:

| Key | Describes |
|-----|-----------|
| `schema` | The format of `project.json` itself |
| `layout` | Where the project's own state lives — `1` in the project, `2` in the data store |

A project whose `project.json` has no `layout` is on `1`, which is what every v2 and M1 project is.
A project created by a bind that finds **no** `user-data/` directory is born on the current layout,
so a new project is clean from its first bind and has nothing to migrate.

**`bind`, `sync`, `update` and `migrate` never relocate memory.** They report that an upgrade is
available — a line on the bind, a `warn` finding in `doctor`, a notice in the session banner — and
stop there. `devteam upgrade` performs it, previewing by default and acting only on `--apply`.

The upgrade is **copy → verify → retire**: every file is copied, every copy is confirmed by sha256,
and only then does the original directory go to `data/quarantine/<date>/<project_id>/`. A populated
destination aborts before anything is copied. A mismatch aborts before anything is removed. There
is no step at which the only copy of a file is in flight.

**Readers resolve through a recorded version, not a fallback chain.** `project.layout()` decides
where memory lives, and `bind`/`sync` write `.dev-team-agents/state-dir` — a one-line pointer file
holding the absolute path — so `scripts/lib/state.sh` resolves it with a single file read. Asking
the CLI would mean a python subprocess on every `state_get`, and those run inside hooks.

## Consequences

### Positive
- No user data moves without an explicit command and a preview the user read first.
- The fallback is bounded by a recorded version instead of living forever in every reader: once a
  project is on layout 2, nothing consults the old path again.
- A new project never has a migration to do, because it is never on the old layout.
- The store-side and project-side paths are resolvable from bash in one read, so hooks pay nothing.
- `installed_version` is stamped by the bind, so the four v2 readers report the truth without being
  repointed — the state-ownership question from the M1 review is answered as a stopgap, and ADR-0007
  still records retiring the key as open.

### Negative
- Two layouts exist in the field indefinitely, since nothing forces the upgrade. Every reader of
  project state has to go through the resolver rather than a constant.
- The pointer file is machine-local and must be regenerated by `sync` — a copied project directory
  carries a pointer to another machine's store until it is re-bound.
- One more concept (`layout`) alongside `schema`, and the distinction has to be explained wherever
  either appears.

### Neutral
- The quarantine copy means an upgraded project's memory exists twice until the user clears
  quarantine, which nothing does automatically.

## Alternatives Considered

| Alternative | Why rejected |
|-------------|-------------|
| Relocate during `sync` | Moves user data as a side effect of an unrelated command, on every bound project at once, with no moment of consent. |
| Dual-write with read fallback for one deprecation cycle | Nothing breaks, but the same fact has two homes and no owner — the exact defect the M1 review found in `installed_version`, and it would never end on its own. |
| Hard cutover with no layout key | Simplest resolver, and it strands the memory of every project that has not yet run the new code. |
| Bump `schema` instead of adding `layout` | An older CLI refuses a newer `schema` outright, which would lock a user out of a project over a data location rather than a format change. |
| Resolve the state directory by calling the CLI from bash | Correct, and it adds a python process to every `state_get` inside every hook. The pointer file is one read. |
