## MEDIUM

### O hook de branch-overlap forka `python3` e re-parseia o cache inteiro uma vez por arquivo editado, contra o "python is forked once" do seu próprio cabeçalho

- **Fingerprint:** `token-branch-overlap-hook-forks-python-and-reparses-cache-per-path`
- **Alvo:** `scripts/hooks/post-tool-use/04-branch-overlap.sh`
- **Evidência:** `:10-12` declara o contrato — "Runs after every edit, so bash gates come first: an edit tool, `branch_overlap_active` not false …, a session id and an existing cache; **python is forked once**, only when all hold, to compare hunks." Mas `:58-73` coleta até 8 caminhos (`while [ "${#PATHS[@]}" -lt 8 ] && [ "$COUNT" -lt 16 ]`) e `:77-80` faz `for P in "${PATHS[@]}"; do MATCHES="$(python3 -I -c '… from devteam import branch_overlap; sys.exit(branch_overlap.main(sys.argv[2:]))' "$LIB" match "$CH_ROOT" "$CH_STATE_DIR" "$P" …)"`. `scripts/lib/devteam/branch_overlap.py:370-371` — `elif len(argv) >= 4 and argv[0] == "match": for name, author in match(argv[1], argv[2], argv[3])` (um único caminho por invocação); `:345` — `cache = jsonio.read_json(os.path.join(state_dir, CACHE_NAME), default=None)` **dentro** de `match()`, logo re-lido e re-parseado em cada fork; `:330-337` — `_working_hunks` forka `git cat-file -e` e `git diff -U0 … HEAD -- <path>`, 2 processos por caminho.
- **Problema:** o contrato declarado é 1 fork; o código faz até 8, cada um pagando o startup do interpretador, o import do pacote `devteam`, uma leitura+parse completa do cache JSON e dois `git`. `branch_overlap.main` recebe um caminho por invocação, então o custo é estrutural, não acidental — e `git diff -U0 HEAD -- p1 p2 …` já aceita múltiplos pathspecs.
- **Por que importa:** o cache é limitado a 50 branches × 200 arquivos × 100 hunks (`branch_overlap.py:46-48`) e é re-parseado N vezes no mesmo evento. Medido nesta máquina (Linux, VM rápida): **25 ms por fork de `python3 -I` com o import** (`for i in 1..5` → `real 0m0.126s`), e o próprio repositório orça "python3 and the state directory cost tens of milliseconds" (`post-tool-use/03-repair-detect.sh:21-23`) — em Windows Git Bash o custo é bem maior. O caminho Claude Code (`Edit`/`Write`/`MultiEdit`, um `file_path`) paga 1 fork e o cabeçalho está certo; um `apply_patch` do Codex ou um `patch` do opencode tocando 5 arquivos paga **5 forks de python + 5 parses do cache + 10 forks de git** (≈125 ms aqui) contra 1 + 1 + 2. Isso em *todo* PostToolUse de edição nos projetos onde o cache existe — justamente os que a feature atende. O cabeçalho é também o único lugar onde esse custo está documentado, e documenta o valor errado.
- **Proposta:** aceitar vários caminhos em `branch_overlap.main` (`match <root> <state-dir> <path>…`, iterando `argv[3:]` com o cache lido uma vez e um único `git diff -U0 HEAD --` com todos os pathspecs) e trocar o laço de `:77-85` por uma única invocação, imprimindo `path<TAB>branch<TAB>author`; corrigir o cabeçalho se o laço for mantido.
- **Impacto positivo:** de N forks de python + N parses de cache + 2N forks de git para **1 + 1 + 2**. Num patch de 5 arquivos: 5→1 fork de python (−100 ms medidos), 5→1 parse de um JSON de até 50×200 entradas, 10→2 forks de git; no teto de 8 caminhos, 8→1 e 16→2.
- **Impacto negativo / risco:** muda o contrato de saída de `branch_overlap match` (hoje `branch<TAB>author`), consumido também pelo caminho `refresh` em `session-start.sh:453` e coberto por `tests/test_branch_overlap.py` — exige atualizar ambos; o loop bash passa a ter de desmembrar por caminho; e um `git diff` com múltiplos pathspecs devolve hunks de todos os arquivos de uma vez, exigindo que `parse_hunks` seja consultado por chave de arquivo (já é um dict por arquivo, então o ajuste é pequeno, mas é código novo num caminho fail-open), e um erro em um caminho passa a ter de ser isolado dentro do python em vez de pelo `|| continue` do bash.
- **Esforço:** Médio

### O hook de idioma reinjeta o mesmo parágrafo de 370 caracteres em todo prompt, sem teto e sem gate de uma-vez-por-sessão

- **Fingerprint:** `token-language-hook-restates-370-char-policy-on-every-prompt-uncapped`
- **Alvo:** `scripts/hooks/user-prompt-submit/04-language.sh`
- **Evidência:** `scripts/hooks/user-prompt-submit/04-language.sh:32` — `echo "[DEVTEAM:LANGUAGE] Reply to the user in ${LANG_TAG} — every message, including the last one of a task and any fixed message a command says to output exactly (code, paths, versions, commands, placeholders and emoji stay as written). Only what a command says to output verbatim stays as written. Documents, code comments, commit messages and the session summary stay in English."` — **370 caracteres** com `LANG_TAG=pt-BR` (medido). `:2-4` declara a intenção: "restates the conversation language on EVERY prompt". Nenhum marcador de sessão: `grep -c "warn-once\|context-shown\|devteam_warn_once" scripts/hooks/user-prompt-submit/04-language.sh` → **0**, enquanto o irmão `scripts/hooks/user-prompt-submit/05-recall.sh:85-86` usa exatamente esse padrão (`SHOWN="${CH_STATE_DIR}/.context-shown-${SESSION}"`) para não repetir ponteiros, e `scripts/hooks/lib/warn-once.sh` já expõe `devteam_warn_once` pronto.
- **Problema:** o lembrete de idioma e a lista completa de exceções (código/caminhos/versões/commits/summary) são reemitidos integralmente a cada prompt. O valor anti-drift está no nome do idioma; a lista de exceções é estável e não muda dentro da sessão. O canal vizinho de hints é limitado a 5 linhas / 1.200 caracteres por prompt (`scripts/hooks/lib/context-hints.sh:29-30`) — esta linha é **31% desse orçamento inteiro**, entregue por fora dele, sem teto e sem deduplicação.
- **Por que importa:** o default do repositório é `"language": "pt-BR"` (`scripts/lib/preferences-defaults.json:2`), então o caminho caro é o caminho **padrão**, não a exceção. 370 chars ≈ 90 tokens por prompt: numa sessão de 40 prompts são ~3.600 tokens de texto idêntico; numa de 80, ~7.200 — repetidos dentro da mesma janela que `CLAUDE-md/preferences.md` governa por `context_window_percent_warning: 55`. O repo já resolveu esse exato problema uma vez (`.context-shown-<session>` no `05-recall.sh`) e este hook não herdou a solução.
- **Proposta:** usar `devteam_warn_once` (ou um marcador `.language-shown-<session>` no state dir, como `05-recall.sh`) para emitir o parágrafo completo no primeiro prompt da sessão e, nos seguintes, só `[DEVTEAM:LANGUAGE] <tag>` (~30 chars), mantendo o fallback atual (parágrafo completo) quando não houver state dir utilizável.
- **Impacto positivo:** 370 → ~30 chars a partir do 2º prompt. Sessão de 40 prompts: 14.800 → **~1.540 chars** (≈3.600 → ≈380 tokens, **−89%**); sessão de 80: 29.600 → ~2.740 chars. Incide em toda sessão de todo usuário com `language` ≠ `en` — o default de fábrica.
- **Impacto negativo / risco:** o drift para inglês que o hook foi escrito para conter pode voltar em sessões longas, porque a forma curta não repete as exceções perto do último prompt — mitigável mantendo na forma curta a cláusula operativa (`Reply in <tag>`) e reemitindo o parágrafo completo após compactação (`pre-compact.sh` pode resetar o marcador). Passa a depender do state dir (hoje o hook não o toca), somando um caminho de erro a um script que hoje faz um único `grep`.
- **Esforço:** Baixo

> **Nota lateral, fora deste eixo:** as duas frases do parágrafo de `04-language.sh:32` sobre saída
> verbatim se contradizem — "any fixed message a command says to output exactly" deve ir em pt-BR
> vs. "Only what a command says to output verbatim stays as written". Vale a um eixo de
> consistência, não a este.
