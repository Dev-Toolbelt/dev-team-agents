# Embeddings and RAG by Provider

Comparison reference for choosing an embedding model and provider-specific RAG features. Model names, dimensions and pricing tiers change frequently — verify against the provider's own docs before committing to a choice; nothing here should be hardcoded into application config without a version pin.

> Detect the provider the project already uses (SDK in the dependency manifest, `*_API_KEY` in env templates) and follow its own documentation. Never introduce a provider the project has not chosen — this file is for the comparison decision, not a default.

## Embedding Models Compared

| Provider | Model family | Typical dimensions | Context limit | Similarity convention | Notes |
|---|---|---|---|---|---|
| OpenAI | `text-embedding-3-small` / `text-embedding-3-large` | Configurable via `dimensions` param (default 1536 / 3072) | ~8K tokens | Cosine, normalized | Native dimension reduction lets you shrink vectors without re-embedding from scratch; large corpus + cost-sensitive → `small` first, escalate only on recall gap |
| Anthropic | No first-party embedding model; recommends **Voyage AI** | Model-dependent (`voyage-3`, `voyage-3-lite`, `voyage-code-3`) | ~32K tokens (varies by model) | Cosine, normalized | `voyage-code-3` is domain-tuned for source code; Anthropic's **Contextual Retrieval** technique (prepend LLM-generated chunk context before embedding) is provider-agnostic but documented against Claude + Voyage |
| Google | `text-embedding-004` / `gemini-embedding-001` | 768 (default), truncatable via Matryoshka representation | ~2K tokens | Cosine, normalized | Requires an explicit `task_type` (`RETRIEVAL_QUERY` vs `RETRIEVAL_DOCUMENT`) — omitting it or mismatching query/document task types silently degrades recall, the Gemini-specific instance of the "symmetry" rule in the main SKILL |
| Cohere | `embed-v4` (multilingual) | Configurable (256–1536), Matryoshka-style truncation | ~128K tokens | Cosine, normalized | Ships a first-party **rerank** endpoint (`rerank-v3.5`) commonly paired with any of the above embedders — reranking model choice is independent of embedding model choice |

Rules that hold across every row above (do not duplicate provider-specific detail into the main `SKILL.md` Embeddings section — it already states these generically):
- A `task_type`/query-vs-document prefix mismatch (Gemini, some Voyage models) is the most common silent recall killer — test query and document embeddings against each other before shipping.
- Matryoshka/truncatable embeddings (OpenAI v3, Gemini, Cohere v4) let you shrink stored vector size after the fact without a full re-embed — check whether the provider truncates client-side (free) or requires a flag at embed time (may need re-ingestion).
- None of the above are interchangeable in the same index — mixing embedding models/providers in one vector column is the "re-embed on model change" failure mode from the main SKILL, just triggered by a provider switch instead of a version bump.

## RAG-Specific Provider Features

| Provider | Feature | What it solves | Trade-off |
|---|---|---|---|
| Anthropic | **Contextual Retrieval** (prepend chunk-specific context generated by an LLM pass before embedding/indexing) | Chunks that lose meaning in isolation (the "context header" problem in the main SKILL, automated via LLM instead of static title/section path) | One extra LLM call per chunk at ingestion time — mitigate with prompt caching on the shared document context |
| Anthropic | Prompt caching (cache_control on stable prefixes) | Repeated large system prompts / retrieved context across turns | Cache writes cost more than a normal call; only pays off with reuse within the cache TTL |
| OpenAI | File Search / Assistants retrieval (managed chunking + vector store) | Skips building a custom ingestion pipeline | Less control over chunk boundaries and reranking than a custom pipeline — evaluate against the Ingestion and Chunking rules in the main SKILL before adopting |
| Google | Grounding with Google Search / Vertex AI Search | Retrieval against a live web or managed corpus instead of a self-hosted vector store | Cedes corpus control; still needs citation verification per the Failure Modes table |
| Cohere | Rerank endpoint as a standalone step after any vector search | Adds reranking without switching embedding provider | Extra network hop and latency per query — same trade-off as the Reranking row in the main SKILL's Retrieval Patterns table |

## Choosing Between Providers

Gate on signals already present in the project, same discipline as vector store selection in the main SKILL:

| Signal | Lean toward |
|---|---|
| Project already calls Claude for generation | Voyage AI embeddings + Contextual Retrieval — same vendor ecosystem, documented integration path |
| Project already calls OpenAI for generation | `text-embedding-3-*` — one API key, one billing surface, native dimension reduction |
| Corpus is source code | `voyage-code-3` or a code-tuned embedding model over general-purpose ones — domain fit dominates provider convenience here |
| Corpus is multilingual | Cohere `embed-v4` or Gemini — both are explicitly multilingual-trained; verify against the project's actual language mix, not the marketing claim |
| No generation provider chosen yet | Do not let the embedding choice force the generation provider or vice versa — they are independent decisions; nothing requires using one company's embeddings with the same company's LLM |

Do not default to same-vendor embeddings + generation without checking domain fit and pricing first — vendor convenience is a tie-breaker, not the primary criterion.
